---
name: release
description: Cuts a release of the current repo, working out the semver bump (major, minor, or patch) from the Conventional Commits since the last tag, then tags and pushes. When no commit calls for a new version, it still pushes the branch, without a tag. Use when the user types /release or asks to cut, ship, tag, or publish a release or new version. Don't use it unasked, since it pushes.
---
1. Find the latest `vX.Y.Z` tag and list the commits since it (`git log <tag>..HEAD`). If there are uncommitted changes, stop and offer to commit them first as Conventional Commits, so the release only holds typed, committed work.
2. Take the bump from the highest-ranking commit: `!` after the type or a `BREAKING CHANGE:` footer is major, `feat` is minor, `fix` or `perf` is patch. If there's nothing but other types (`chore`, `docs`, `ci`, ...), there's no version to cut, but still push the branch, with no tag and the same rules on a rejected push as step 4, so all pending commits go out. Then report that nothing needed a release and what was pushed, and stop. For a major bump, confirm with the user first: a new major, or 1.0.0 from 0.x, is their call.
3. Update every file that holds the current version (`package.json`, `pyproject.toml`, `Cargo.toml`, plugin manifests, etc.). If there's a changelog, add an entry in its format from the `feat` and `fix` subjects. Run the project's checks if it has any, and stop if one fails. Commit these as `chore(release): vX.Y.Z`. If nothing needed updating, skip the commit and tag the current one.
4. Tag `vX.Y.Z`, matching the existing tags (lightweight or annotated). Push the branch, then the tag. If a push is rejected, stop and tell the user; don't force-push, rebase, or merge.
5. Report the new version, which commits set the bump, and what was pushed.
